# しゅがけストーキング

しゅがけ（Sugar Cage）IP のレトロ風アクション。単一 HTML / 外部依存なし。

実機テスト: https://ghbe2.github.io/sc_stalking/

---

## 見た目

**ドットマトリクス液晶**を土台にしつつ、モノクロは卒業して**役割ごとに色を振っている**。
背景と地形はこの8色だけで、**中間色は持たない**。

| | |
|---|---|
| `bg` / `off` / `dim` | 液晶の地と影と中間 |
| `ink` | 主線・シルエット |
| `warn` | 危険（網・警告・ハート） |
| `gold` | 拾えるもの（空き缶・おにぎり・チーズ） |
| `aqua` | 水（水たまり） |
| `plum` | トウカとヤツメウナギ |

色を見ただけで「取るもの」「危ないもの」「トウカ側のもの」が分かる。

### キャラは描き下ろしのドット絵を使う

キャラと拾いものだけは、`images/` の絵から起こしたスプライトを使っている。
液晶の雰囲気を壊さないよう、変換で3つの決まりを守らせている。

1. **半透明を作らない。** 閾値で切って、透けるか透けないかのどちらかにする。
   合成が起きないので、画面に中間色が生まれない
2. **1体15色まで**（スーファミの規律。起動時の検査もこれを見ている）
3. **パレット全体を液晶の地へ14%寄せる。** 元絵は白地で描かれているので、
   そのまま置くと浮く

それでも**白いTシャツと淡い肌は地の薄桃に近く、輪郭が消えた**。
輪郭線は足さない方針なので、代わりに**地に近すぎる色だけを地から引き離している**
（差が一定以下の色を最大3割暗くする）。塗りだけで輪郭が立つ。

実際に測ると、5画面のどの点も「8色パレットか、スプライトの色」のいずれかで、
**想定外の色は0**。合成による中間色は生まれていない。

縮小のしかたにも理由がある。**LANCZOS で一気に縮めると輪郭に「鳴き」が出て、
周りと繋がっていない単独の点が残る**。手で置いたドット絵にはこれが無いので、
あるだけで粗く見える。4倍手前まで段階的に落として、最後は面積平均で均し、
そのうえで**浮いた1ドットを消して**いる。

寸法は**実機基準**。縦持ちスマホは仮想 150x320 になり、レーン幅は約37px。
ここを基準に決めているので、大きい画面では余白が増えるだけで崩れない。

    python tools/mkspr.py          # images/ を読んで index.html へ直に差し込む
    python tools/mkspr.py --sheet  # 確認用の拡大シートも出す

差し込み先は index.html の `ART:BEGIN` 〜 `ART:END`。**単一HTMLのまま**にするため、
別ファイルにはしていない。絵を描き直したら、このコマンドを流すだけで反映される。

### 1ドットを必ず整数個の実ピクセルにする

拡大を画面いっぱいに合わせると倍率が端数になり、**3px の点と4px の点が混ざって
輪郭がガタつく**。これがジャギの正体だった。

倍率を先に整数で決め、幅のほうをその倍率に合わせている。
375x812 / dpr2 の端末なら**実ピクセルでちょうど5倍**、左右の余白は0。

格子（ドットマトリクスの罫線）は**やめた**。絵が入ったことで、罫線は
質感より先に「見づらさ」として効いてしまった。ガラスの映り込みと周辺減光だけ残している。

トウカ本人は最後まで出てこない。**画面に出てくるのはヤツメウナギ**で、

## 案内は、その場に短く出す

説明画面を挟むより、**対象の隣に短い札を出す**ほうが手が動く。
点滅させて視線を呼び、地を敷いてから字を置くので背景に紛れない。

| 画面 | 出るもの | どこに |
|---|---|---|
| 路地 | `ESCAPE!` | マンホールの真上。逃げ道だと分からないと、そもそも飛び込まない |
| 落下 | `HOLD L / R` | 最初の2.2秒だけ |
| 下水 | `HOLD = DUCK` → `RELEASE = JUMP` | 入口の300px。操作そのものを言う |
| 下水 | `GRAB!` | 梯子の下端。足場から跳ばないと届かないので、気づかないと素通りする |
| 昇り | `TAP!` | ミナリの上。連打しないと群れにおにぎりを食われる |
| トウカ | `TAP L / R TO DODGE` | 最初の2.4秒。即死の画面なので、知らないまま入らせない |

## 難易度の時計は画面ごとに巻き戻る

混み具合・監視の激化・下水の速さは、**その画面に入ってからの秒数**で決まる
（`S.screenT`）。通しの時間で回していたころは、下水や昇りを挟んで路地へ戻ると
**いきなり最高難度から始まって**いた。

    路地で40秒粘る    → 混み1.00 / 監視1.00 / 敵速 x2.75
    下水と昇りを経て戻る → 混み0.00 / 監視0.00 / 敵速 x1.35

下水の速さも同じで、40秒粘ったあとに入っても入口の 58px/s から始まる。

> **注意。** これで**ステージを重ねても難しくならなくなった**。
> マンホールの間隔は820px・走る速さは68px/s なので、毎回すぐ飛び込めば
> 1回の路地は約12秒、混み0.35 / 監視0.55 までしか上がらない。これが何周しても同じ。
> 周回そのものに上がり幅を持たせるなら、ステージ数に応じて時計の開始位置を
> 底上げする（例: ステージごとに +3秒）のが素直。

## 路地の画面

ミナリが路地を上へ走る。縦スクロール・4レーン・奥行なし。

### 操作

画面の**左半分／右半分をタップ**すると、その方向へ **1列ずつ**移動する。長押しで連続移動。
デスクトップは ← → キー。

### ルール

| | |
|---|---|
| 子供 | 前から歩いてくる（**速い** 116px/s）。触れるとハート -1。同じ列に続けて出る（たむろするガキ） |
| 男 | 前から歩いてくる（**遅い** 92px/s）。**ときどき立ち止まる**。触れるとハート -1 |
| 女 | 横切ってくる。触れると叫ばれて、どこかの列に**監視**がつく |
| 監視 | その列を見張る。監視列に居続けると発見され、トウカの画面へ |
| 空き缶 / おにぎり | 拾うとスコア |
| マンホール | 飛び込むと**落下**へ。おにぎりを拾ってハートを回復し、次のステージへ。**逃げ道なので他より大きく、飛び込める間合いも倍に深い**（外すと次まで約12秒あるため） |

- **ハート3個。尽きたら GAME OVER。**
- 生き延びているだけでスコアが入り、**粘るほど毎秒のレートが上がる**（+10/s → +55/s）。
- 時間が経つほど人混みが詰まり、歩いてくる連中が速くなる（**34秒で x1.35 → x2.75**）。
  **落ちているアイテムは速くならない。**
- **序盤がぬるすぎたので、始まった時点ですでに速い**（x1.0 ではなく x1.35 から）。
  ぬるい時間を短くするより、**ぬるい時間を無くす**ほうが手触りが変わる。
  同じボットで測って、生存 30.2秒 → **24.1秒**、消費ハート 2.05 → 2.30。
- 監視は徐々に増える。**最大4列まで**——1列は必ず空ける（難易度の問題にとどめ、理不尽にしない）。
- 監視は**画面の上に小さな目**が出て、その列がハッチで示される。
- 「見られている」時間はミナリ側に1本。列を移っても引き継ぐので、監視列を渡り歩いても逃げられない。
  **ゲージは下水の気配ゲージと同じ見た目**（画面上端の帯）で、両フェーズで読み方が揃えてある。
- 開幕は約1秒、誰も来ない。人は必ず画面の外から降りてくる。
- 同じ列に子供と大人を混ぜない（速さが違うので追いついて重なる）。保証則で検査している。

### 難易度は画面ごとに登り直す。ただし1周ごとに1割きつくする

難易度の時計は**その画面に入ってからの時間**で回している。通しの時間で回すと、
下水や昇りを挟んで路地へ戻ったとき、**いきなり最高難度から始まってしまう**。

ただし登り直すだけにしたら、**いつまでも同じ坂で、ほぼ無限に生き残れる**ようになった。
そこで**同じ画面に戻ってくるたびに坂を1割きつくする**（`stageGain: 1.10`）。
同じ時間で難易度が先へ進むので、やがて登りきってしまう。

| ステージ | 坂の倍率 | 路地の生存 | 消費ハート |
|---|---|---|---|
| 1 | 1.00 | 24.8秒 | 2.25 |
| 5 | 1.46 | 27.9秒 | 2.55 |
| 10 | 2.36 | 23.6秒 | 2.60 |
| 15 | 3.80 | 21.7秒 | 2.95 |
| 20 | 6.12 | 17.9秒 | 2.80 |

坂を登りきった（混み具合が上限に達した）あとは、**そのぶんが速さと人混みに
直接乗る**（`overdrive`）。上限で頭打ちになると、そこから先のステージが
無意味になってしまうため。

下水も同じ扱い。潜った距離に倍率がかかるので、ステージが上がるほど早く
気配に追いつかれる（ST1で1586px → ST16で1070px）。

**通しで遊ばせて確かめた。** 全画面を自動で遊ぶボットを回すと、到達ステージは
1〜8、20〜345秒で必ず終わる。以前のように延々と続くことはなくなった。
早めにマンホールへ逃げる打ち方のほうが遠くまで行けるので、
「いつ抜けるか」という判断がそのまま腕前になっている。

### この画面の役割

**路地は生存に徹する。** 危険を冒してスコアを稼ぐのはトウカフェーズの役目。
唯一の判断は「**いつマンホールで抜けるか**」。粘るほどスコアは伸びるが、生還率は落ちる。

## 落下の画面

マンホールに飛び込むと縦穴を落ちる（約5秒）。**上下が路地と逆**で、おにぎりが下から昇ってくる。
拾うとハートが1個戻る（満タンならスコア）。

**落下中はレーンを使わない。** 押している方向へ流れ、指を離しても慣性で少し流れ続ける。

当初は移動を極端に鈍くしていたが、**おにぎりの間隔（1.2秒）で横に動ける幅が40px しかなく、
画面幅256px のどこにでも湧く的にはそもそも届かなかった**。狙って取れるのが2割では
「回復の機会」として成立しないので、届く速さに直した（最高110px/s。指を離してから
約31px 流れる）。同じボットで測って **21% → 83%**。人の指なら半分強といったところ。

おにぎりは4個で位置は完全ランダム。**拾えたら儲けもの**ではあるが、**狙えば応えてくれる**
重みに変えてある。

**ハートを取り戻せるのはここだけ。** 監視に見つかってトウカへ行くとこの画面を通らないので、
安全な道を選んだ者だけが回復する。低リスク低リターン／高リスク高リターンを、
点数だけでなく体力でも表している。

落ち始めの1.6秒だけ、**マンホールの縁からヤツメウナギが覗いて手を伸ばしてくる**。
崖から落ちる者へ差し出される手だが、掴まれることはない。追われている、という
気配だけを置く演出で、当たり判定は無い。

ミナリはこの画面でだけ大きく描く。他に見るものが少ないので、顔を見せる場面にしている。

落ちた先は下水。

## 下水の画面

横スクロール。ミナリは自動で右へ走り、**入力は1つだけ**。

| | |
|---|---|
| 押しっぱなし | しゃがむ（同時にジャンプを溜める） |
| 放す | 溜めたぶん跳ぶ |

地面は途切れない。出てくるのは蝙蝠の**2隊形**と、水たまり、チーズだけ。
蝙蝠はふさぐ高さの帯が違うので、**伏せるか跳ぶか**が一意に決まる。

| 隊形 | ふさぐ帯 | かわし方 |
|---|---|---|
| **high** | 14〜92px | **伏せる**（どう跳んでも抜けられない） |
| **low** | 0〜14px | **跳ぶ**（溜めなしの跳躍で余裕をもって越えられる） |

溜め量の精度は要求しない。溜めは跳ぶ高さと距離を決めるだけで、**当てにいく精度ではなく
「いつ放すか」だけを問う**。当たるとハート -1。

| | |
|---|---|
| **水たまり** | 踏んでもダメージは無いが、トウカに位置が伝わる（+30）。跳べば避けられるが、**跳び越えられない広さのものもある** |
| **チーズ** | 跳んで取る（走っているだけでは届かない）。+60点 |

蝙蝠は**当たりやすすぎた**ので、体を8px・蝙蝠を9pxに絞り、迫る速さも落とした
（当たり幅 21→17px、接近 86→80px/s）。

蝙蝠は向かって飛んでくるので、地形（58px/s）より速く迫る（80px/s）。
譜面に書いた位置で出会うよう、寄る距離を足した所から飛ばしている。
**隊形どうしは必ず130px以上あける**（跳んだ着地点に次が来ると理不尽になるため）。

low は当たり判定の **10px 手前（約0.12秒）** で踏み切らないと間に合わない。
high は逆に、抜けきる前に放すと当たる。

### 伏せる → 跳ぶ の繋ぎ目

**この並びだけが飛び抜けてきつかった。** 押しっぱなしを一度切り、跳ぶために溜め直す、
という持ち替えが要るのに、譜面ではこれが他と同じ 135px 間隔で何度も出ていた。
最奥の接近速度（124px/s）だと **1.09秒**しかない。

`batSwapGap`（200px）として**この並びにだけ広い間隔**を要求し、保証則で検査するようにした。
あわせて譜面を組み替え、**7回 → 5回**に減らしたうえで間隔を 210〜220px へ広げている
（猶予 **1.09秒 → 1.70秒**）。減らしたぶんは「伏せっぱなしで抜ける」譜面に置き換えた
——持ち替えを迫らず、密度で押す。

同じ「難しい」でも、**判断が難しいのは良く、持ち替えが間に合わないのは悪い**。
後者だけを狙って削っている。

### 何を避ければいいのかを見せる

蝙蝠が点在して見えて、**伏せるのか跳ぶのかが判断できなかった**。
帯を塞いでいるのに、その帯が見えていなかったのが原因。

- **塞いでいる高さの帯そのもの**を市松のドットで描く（市松なので中間色は作らない）
- 蝙蝠を大きくして、帯を**隙間なく埋める**ように積む
- 通れる側に**矢印**を出す。伏せるのか跳ぶのかを記号ひとつで言い切る
- ミナリの**足元に影**を落とす。跳んでいる高さは、影との距離でしか読めない

### 縦の単位を2倍にした（遊びは変えずに）

ミナリを絵の大きさで描くために、下水だけ**縦の単位を2倍**にしてある。
立ち15→30px、伏せ8→16px、帯14/92→28/184px、足場28→56px、梯子64→128px。

**重力と初速を同じ倍率にすると、頂点は2倍になるが滞空時間は変わらない**
（頂点 = v²/2g は f倍、滞空 = 2v/g は不変）。横の速さは触っていないので、
1回の跳躍で進む距離も同じ。つまり**譜面も間合いも難易度も一切変わらず、
見た目だけが大きくなる**。

実測でも滞空 0.846秒・跳躍距離 49.1px・足場に乗れる39%・梯子を掴める81% と、
2倍にする前と完全に一致している。

横方向（体の幅・蝙蝠の幅・足場の長さ・梯子の幅）は**据え置き**。
ここを一緒に倍にすると当たり判定が変わってしまう。

### 浮いた足場と梯子 — 乗るか、下を行くか

**足場は宙に浮いている**（地面から56px。ミナリの背丈のほぼ2倍）。一方通行で、**下は素通りできる**。
跳んで上から降りてきたときだけ乗る。つまり毎回、**乗るか下を行くか**を選ぶことになる。

- **何もしない** → 足場に触れずに下を走り抜ける
- **溜めて跳び乗る**（溜め25%）→ 足場の上の**高いチーズ**が手に入る。端まで行けば地面に落ちる
- **乗ってからさらに跳ぶ**（ほぼ溜めなし）→ **梯子**を掴んで地上へ（ステージ+1）

梯子は128pxに吊ってあり、**地面からの最大到達は123px**なので、どう溜めても地面からは届かない。
足場に立っているだけ（頭86px）でも届かない。**乗って、さらに跳んだときだけ**手が届く。

この「乗る／掴む」は当初きつすぎた。**掴みたいのに掴めない**という声が出たので、
跳ぶ位置と溜めの全組合せを総当たりして、成功する割合そのものを測って直した。

| | 旧 | 新 |
|---|---|---|
| 足場に乗れる組合せ | 24% | **39%** |
| 足場から梯子を掴める組合せ | 75% | **81%** |

効いたのは足場と梯子を**両方下げた**こと（40→28px / 84→64px）。低くすると乗るのは楽になるが
足場から梯子までが遠のくので、あわせて跳躍の上限も下げ（258→220）、
「地面からは届かない」という条件を保ったまま両方をゆるめている。
足場は104pxに広げ、梯子の掴み幅も28pxに広げた（助走と猶予）。

**水たまりがトウカへの導線。** トウカはナマズで、水と地面を伝わる振動を直接感知する。
踏むと気配が +20 溜まり、静かにしていれば薄れる。ただし**潜るほど薄れ方が鈍くなる**
（入口 6.0/s → 最奥 1.8/s）。トウカが耳を澄ましていく、という理屈で、
**上手く跳んでも いつかは追いつかれる**。跳び越えられない広さの水たまりもあるので、
完全には避けきれない。

梯子の配置は「その位置に隊形が無いこと」で決めるが、**蝙蝠は向かって飛んでくるので現在位置
では判定にならない**。プレイヤーと出会う位置を逆算して空きを判定している（実測で、梯子の
真下を通る瞬間の最寄り隊形は 92px 先）。

実測（6ラン平均・被弾は無視して気配だけ見た場合）:

| 立ち回り | 潜れた時間 | 到達 | 終わり |
|---|---|---|---|
| 濡れるに任せる | 23秒 | 1800px | 全ラン トウカ |
| 跳べる水は跳ぶ | 58秒 | 5200px | 全ラン トウカ |
| 2つ目の段差で上がる | 20秒 | 1540px | 全ラン 地上へ |

腕で倍ほど潜れるが、**どう上手くやっても必ず追いつかれる**。

溜めなしで高さ22px、最大溜めで高さ64px跳ぶ。

**保証則**として機械的に検査している項目:

- 各隊形にちょうど1つの正解があること
  （high は伏せてのみ・跳んでも抜けられない／low は伏せでは抜けられない）
- low が溜めなしの跳躍で余裕をもって越えられるか（溜め量の精度を要求しない）
- チーズが「走っては届かず最大溜めなら届く」高さか
- 梯子が「地面からは絶対に届かず／段差に立つだけでも届かず／段差から跳べば届く」高さか
- 高いチーズが「段差に立つだけでは取れず／地面からでも最大溜めなら取れる」高さか
- 隊形どうしが `batMinGap` 以上あいているか（跳んだ着地点に次が来ない）
- 跳ぶ隊形の着地点に水たまりが来ていないか（避けようがなくなる）
- 水たまりの幅が「跳べるか微妙」な中途半端になっていないか

高い群れを抜けきる前に放すと当たる（抜けるまで約4px＝0.07秒の我慢）。

通算時間はリセットされないので、ステージを重ねるほど難しくなる。

## 昇りの画面

下水で梯子を掴むと、縦穴を昇る。**連打で登る**（タップ位置でも長押しでもない、3つ目の動詞）。

下から**ヤツメウナギの群れ**が這い上がってくる。追いつかれても傷は負わないが、
**追い抜かれた先のおにぎりは食われてなくなる**。群れは加速するので、のんびりしていると
必ず抜かれる。

| 連打 | かかる時間 | おにぎり2個 |
|---|---|---|
| 0〜2回/秒 | 8〜15秒 | 食われる／食われる |
| 3回/秒 | 6.7秒 | **取れる**／食われる |
| 4回/秒〜 | 5.7秒以下 | **取れる／取れる** |

おにぎりは1個につきハート +1（満タンならスコア）。**ダメージは無い**。速さの差は
回復の有無だけに出る。落下の画面が「拾えたら儲けもの」だったのと対になっている。


## トウカフェーズ

路地で監視に見つかるか、下水で気配が積もりきると、ここへ落ちる。**奥から手前へ逃げる**。3列。

### 画面と画面のあいだに一枚挟む

**切り替わった瞬間から操作が変わる。** 知らないまま放り込むと「難しい」ではなく
「分からない」で失敗する。作りたいのはそれではないので、次の画面の名前と操作を
一枚出して、触れたら始まるようにした。

操作は**絵で見せる**。字だと読まない。左右タップ・押しっぱなし・連打を、
指の丸で描き分けている。下水だけは2コマにして、押している間は伏せ、
放すと跳ぶ、をミナリの絵で見せる。

**このあいだ、難易度の時計は止まっている。** 読んだ人が損をしないため。

副産物として**BGMの重なりも消えた**。落下と昇りを無音にしたうえで、
説明の一枚が無音の間になるので、境目で必ず前の曲が終わりきる。
実時間で全画面を回して計測したところ、**2曲が同時に聞こえたフレームは 0/2700**。

### 奥行きを作るのが、この画面の仕事

**道も壁も描かない。大きさの差だけで奥行きを見せる。**

最初は一点透視の廊下を描いていた。壁・稜線・列・床を消失点へ収束させる、
教科書どおりのやつ。だが線を引くほど**方眼に見えて、キャラの邪魔になった**。
全部消して、残したのは**キャラと足元の影だけ**。それで奥行きは伝わる。

影は「道」ではなく「床がある」ことだけを示すもの。これが無いと3人とも宙に浮く。
影の大きさが奥行きの手がかりにもなる。

一度、トウカをミナリのすぐ後ろに並べて両方を大きく描いたが、**奥行きが消えて
ただ2人が縦に並んだ画になった**。「後ろにいる」は距離で見せるものだった。

**大きさと立ち位置は、遠近から逆算して決めている。** 一点透視では

    見かけの背丈 h = 実際の背丈 × f / 奥行き
    足元の位置   y = 地平線 + 目の高さ × f / 奥行き

なので **(足元 − 地平線) ÷ 見かけの背丈** は、同じ背丈のものならどこに居ても
一定になる。ミナリの大きさと立ち位置を決めた時点で**地平線が決まり**、
そこから他のキャラの大きさも立ち位置も一意に出る。

背丈の比は ミナリ1.0 / トウカ1.35 / 部下1.05。同じ奥行きに並ぶので、
2人を横に置いても不自然にならない。

| | 大きさ | 位置（仮想150x320） |
|---|---|---|
| ミナリ | 126x140 | 足元 y278。画面の4割強を占める |
| トウカ | 54x74 | 足元 y150（背丈から自動で決まる） |
| 部下 | 44x58 | トウカの右。投げ手はひとりだけ |
| 網 | 14x11 → 30x28 → 56x52 | 3段階で大きくなる＝近づいて見える |

地平線は y68。ミナリ140px・足元278・目の高さ1.5 から出た値で、
この3つを変えると全部が動く。

手前の列は少し内側へ寄せている（等分の0.78倍）。ミナリが126px幅なので、
素直に等分すると端の列で半分が画面の外へ出る。

**スプライトは一度だけ焼いて、以後は貼るだけ。** 1ドットずつ fillRect すると、
126x140 のミナリだけで毎フレーム1万回以上呼ぶことになり、この画面で 9.04ms
（60fpsの予算16.7msの半分超）かかっていた。焼いて **0.58ms**。
1:1 で貼るので色は混ざらない。

### 逃げ方は路地と別物にする

当初は路地と同じ「触れた側へ1列ずつ」だったが、**それだと路地と遊びが変わらない**。
ここは**真ん中が定位置**で、触れた側へ**ひょいと避け、勝手に戻ってくる**ようにした。
居座れないので、避けるのは一瞬だけ。押しっぱなしで留まられると元に戻ってしまうため、
この画面だけ長押しの連続移動（`holdRepeat`）を使っていない。

定位置が真ん中になったぶん、**そこを突かないと「見ているだけ」の時間**になる。
1本のときは62%、2本のときは72%の確率で真ん中を含める。
残りの「両脇を同時に指す」ときは、**動かないことが正解**になる。

| | |
|---|---|
| 反応0.15秒 | 真ん中に居る時間 **58%** |
| 反応0.35秒 | **73%**（無駄な避けをしないぶん、真ん中に長く居る） |
| 無操作 | **100%**。放っておけば必ず真ん中 |

### 投げ1回 ＝ 避け1回

**避けの長さを自前の時計で持たない。** 網が飛んでいる間は出たまま、着弾したら
一拍（0.14秒）置いて戻る。だから**網が速くなれば、戻るのも同じだけ速くなる**。

そのために、投げも1回ずつ完結させている。**前の網が飛んでいるうちは次を投げない。**
重なると「戻る前に次が来る」ことになり、投げと避けの1対1が崩れるため。

| | |
|---|---|
| 予告（指差し） | 0.62秒 → **0.30秒** |
| 飛翔 | 0.46秒 → **0.28秒** |
| 着弾から次の予告まで | 1.05秒 → **0.18秒** |
| 1周期 | 約2.13秒 → 約**0.76秒** |

終盤の猶予は予告+飛翔で **0.58秒**。反応の遅れを変えたボットで測ると、
**0.55秒までは 30/30** で抜け、0.60秒で 14/24、**0.65秒で 0/24** になる。

一度これを 0.40秒（予告0.20+飛翔0.20）まで詰めたことがあるが、
**並の反応速度だと厳しい**という指摘を受けて戻した。ボットの限界も
0.40秒付近にあり、実際そこが線だった。ボットは**どの列が空いているかを
常に知っていて、判断に時間を使わない**ので、人はこれより必ず遅い。
限界のすぐ手前に置くのではなく、**判断のぶんの余白を残す**ことにしている。

**投げの瞬間、ミナリは必ず真ん中に居る。** 避けが残っていてもそこで畳む。
投げは「飛んでいる網が無いとき」にしか起きないので、戻した先で当たることはありえない。
反応0.15〜0.45秒を通して 1421回の投げを観測し、**違反0回**。

以前は 0.75秒固定にしていたが、**反応が速いほど死ぬ**という逆転が出ていた
（反応0.15秒で 0/30、0.35秒で 30/30）。予告の頭で避けると、網が届く前に
真ん中へ戻されて当たっていたため。周期に紐づけたことで、この問題ごと消えている。

足元には**戻り先の印**と、避けている間の印を出している。

画面は**ミナリが主役**で、こちらへ走ってくる姿を大きく描く。トウカは奥に小さく立って
いるだけ。列は奥へ行くほど中央に寄り、路面が手前へ流れる。

**トウカは自分では追ってこない。** 奥に立って、指を差すだけ。差された列へヤツメウナギが
網を飛ばす。つまり**指差しがそのまま着弾予告**になっていて、予告が演出ではなく
キャラの所作そのものになっている。

| | |
|---|---|
| 指差し | 序盤 0.62秒 → 終盤 0.20秒（読む時間が短くなる） |
| 網の飛翔 | 0.46秒 → 0.20秒（終盤ほど速い） |
| 着弾から次の予告まで | 1.05秒 → 0.12秒 |
| 終盤 | **常に**2列を同時に指す |

2本に入ったら、そこから先はずっと2本にしている。増えたり減ったりすると
「今は何本か」を毎回読み直すことになり、反射の勝負にならない。
実測でも前半196回はすべて1本、後半230回はすべて2本、例外0。

**網に当たったら即 GAME OVER**（ハートは関係ない）。15秒逃げ切れば **+2500点**と
ステージ+1で路地へ戻る。路地1ステージがおよそ900〜1500点なので、2ステージぶんの重み。

**必ず1列は空ける。** まだ当たっていない網は飛行中のものも「塞がっている列」として数える
（予告中だけで数えると、全列が同時に塞がる瞬間ができてしまう）。5400フレーム観測して
空き列の最小値は 1/3 だった。

### 予告なしで網が飛んでいた（修正済み）

2列同時に投げるようになった途端、**予告の出ていない列にも網が来る**という不具合があった。
原因は、指差している列を**1つしか覚えていなかった**こと。2本が同時に予告に入ると
後から処理したほうで上書きされ、もう1本は無言で飛んできていた。

指差し中の列を**配列で全部持つ**ように変えて、予告の腕も着弾の帯も本数ぶん出す。
回避ボットで40走・網538本を通して、**予告なしで飛んだ網は0本**（2列同時に指していた
フレームは2311）。

即死の画面で予告が出ないのは、難しさではなく理不尽なので、ここは保証則の対象に近い扱いにしている。

## 音

**音声ファイルは持たない。** 単一HTMLを保ちたいので、矩形波と雑音だけで合成している。
ピコピコの出自がそもそもこれなので、絵よりも素直にレトロへ寄る。

| | |
|---|---|
| 移動・連打 | 短い矩形波。操作した手応えだけ |
| 拾う / 回復 | 上がる2〜3音。回復は三角波でやわらかく |
| 被弾 | 下がる鋸波＋雑音 |
| 叫ばれる | 上がって下がるサイレン |
| 跳ぶ / 着地 / 水 | 上がる矩形波 / 低い雑音 / 高い雑音 |
| 予告 / 網 / かわした | 高い点 / 擦れた雑音 / 低い短音 |
| 掴まる / ハート切れ | 下がる4音 |
| 梯子・逃げ切り | 上がる4音 |

ブラウザは利用者が触るまで音を鳴らせないので、**最初の入力で起こしている**。
入切は画面の外のボタン（♪）か `M` キー。画面のタップは操作に使うので、
切り替えを画面内には置かない。設定は localStorage に残る。

### BGM は3曲。場所が続いている画面は曲も続ける

| 曲 | 使う画面 | 長さ | 大きさ |
|---|---|---|---|
| `路地フェーズ.mp3` | 路地 | 5分23秒 | 2.77MB |
| `下水フェーズ.mp3` | 下水 | 3分19秒 | 1.73MB |
| `トウカフェーズ.mp3` | トウカ | 2分15秒 | 1.15MB |

**落下と昇りは無音。** ここに曲を割り当てると、5秒の落下と15秒の昇りを挟むたびに
切り替えが起きて、常に2曲が混ざって聞こえていた。

**それでも消えなかった。** クロスフェードをやめても、下水で2曲が重なる。
原因は `play()` が返す約束で、**これが解決する前に `pause()` を呼んでも効かない**
ブラウザがある。音量を0にするだけでは、鳴り続けたまま次の曲が重なる。

いまは重ねない作りにしてある。

- 曲が変わった瞬間に、**他は全部止める**（すれ違わせない）
- 止めるときは**約束の完了を待ってから** `pause()` する
- そのうえで**毎フレーム、鳴っていてはいけないものを拾って止め直す**

実時間で全画面を回して計測し、**同時に鳴った最大本数は1本、2本以上だった
フレームは 0/651**。DEBUG 表示にも本数を出しているので、実機で疑わしければ
そこで確認できる。

落下はマンホールに飛び込んだだけで**まだ路地の続き**、昇りは**地上へ出るまで下水の中**。
だから曲を分けない。

**曲は画面ではなく曲そのもので持っている。** 画面が変わっても同じ曲なら鳴らし直さない。
落下のたびに路地の曲が頭から始まると、繋がりが切れてしまう。
切り替えは1.6秒かけて音量で渡す（前の曲は0になった時点で止める）。

**64kbps モノラル / 32kHz に落としてある。** 元は 160〜180kbps ステレオで
3曲13.53MBあり、スマホの回線だと画面に入ってから鳴り出すまで待たされた。
落として **5.65MB**（1/2.4）。長さは1ミリ秒も変わっていない。

    ffmpeg -i 元.mp3 -ac 1 -ar 32000 -b:a 64k -map_metadata -1 出力.mp3

読み込みは `preload="none"`。使う画面に入って初めて落とす。

ループは `loop=true` のまま。ブラウザによっては継ぎ目に一瞬の無音が入るが、
Web Audio で繋ぐと起動時の復号とメモリを食うので、いまはこのままにしている。

## これから作るもの


画面の切り替えは `enterAlley()` / `enterFall()` / `enterSewer()` / `enterClimb()` /
`enterTouka()` / `finish(how)` に集約してある。

- 安全な周回: **路地 → 落下 → 下水 → 昇り → 路地（ステージ+1）**
- 捕まった場合: **路地 or 下水 → トウカ → 逃げ切れば路地（ステージ+1、+2500点）／網に当たれば GAME OVER**

残っているのは BGM。

## 開発用

画面右上の `≡` から:

- **seed** — 同じコースを再現する
- **開始ステージ** — 押すたび 1〜8 を巡回。選ぶと通算時間もそのぶん進んだ状態で始まるので、
  終盤の難易度をすぐ試せる（タイトルにも表示される）
- **落下を見る** / **下水を見る** / **昇りを見る** / **トウカを見る** — その場でその画面へ飛ぶ
- **DEBUG** — 内部数値の表示

タイトル画面の右下にビルド番号（例 `0812A`）が出る。実機で古いキャッシュを見ていないか、
ここで確かめられる。更新したら `index.html` 冒頭の `BUILD` を上げること。

数値はすべて `CONFIG` に集約してあり、`ramp`（人混み・点の入り）と `watchRamp`（監視）は
独立した時計で走る。
